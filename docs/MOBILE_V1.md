# BookReader Mobile V1 产品蓝图

> 状态：产品方案冻结稿（第一版）
>
> 目标：先明确手机端产品结构和交互边界，再逐步拆分 Codex 施工任务。  
> 本文档不要求产品负责人理解 React、Tauri、epub.js、OneDrive Graph 等具体实现。

---

## 1. 这次 Mobile V1 要解决什么

当前手机端最大的问题不是“功能太少”，而是桌面端的信息结构和交互方式被压缩到了小屏幕上，导致：

- 首页信息密度和视觉权重不合理；
- 侧边栏、搜索、导入、排序等低频功能长期占据显眼位置；
- 阅读页像“工具软件”，顶部按钮过多、正文有明显容器感；
- 选中文字后的 BookReader 操作条与 iOS 系统菜单互相抢空间；
- 笔记页可用但过重，很多内容长期处于“编辑表单”状态；
- 设置页暴露了过多 OneDrive、授权、诊断、同步细节；
- 云同步已经变成阅读前的人工任务，严重阻塞“打开就读”。

Mobile V1 的目标不是加更多功能，而是让 BookReader 成为一个：

**打开快、读得安静、记录顺手、同步不用操心的私人阅读工具。**

---

## 2. 不可违反的产品原则

### 2.1 Desktop UI 与 Mobile UI 明确分离

BookReader 仍然是一个项目，共享图书、阅读进度、笔记和同步能力，但：

- Desktop 保留自己的桌面布局与交互；
- Mobile 拥有独立的手机布局与交互；
- 不再依赖大量响应式 CSS 把桌面 UI 强行压缩成手机 UI；
- 修改 Mobile UI 时，默认禁止顺手修改 Desktop UI；
- 如果某个手机需求必须修改共用能力，Codex 必须先说明原因、影响范围和兼容风险，再决定是否修改。

这不是维护两套 Git 项目，而是：

**一个产品，共用底层，两套明确独立的 UI。**

### 2.2 本地优先，云同步不得阻塞阅读

正常使用流程必须是：

**打开 BookReader → 本地书库立即可用 → 直接继续阅读 → OneDrive 后台自行同步。**

无论发生：

- 没网；
- OneDrive 临时不可用；
- 登录状态过期；
- 同步失败；

都不应该阻止用户：

- 打开已经下载的图书；
- 阅读；
- 保存阅读进度；
- 高亮；
- 写感悟。

新产生的数据先安全保存在本地，网络恢复后再同步。

### 2.3 稳定体验优先于功能完整

Mobile V1 不为了“功能列表完整”牺牲稳定性。

当前左右分页尚不稳定，因此：

- Mobile V1 默认以连续上下滚动作为稳定阅读方式；
- 分页功能等真正稳定后再恢复；
- 不为了修分页继续破坏已经可用的阅读体验。

### 2.4 视觉权重应匹配真实使用频率

高频功能显眼，低频功能后退。

例如：

- 继续阅读：高频，首页第一屏可见；
- 导入：需要，但不是每天使用，缩成“+”；
- 搜索：目前缺少真实高频场景，不常驻首页；
- 排序/筛选：目前无必要，不常驻；
- OneDrive 诊断：开发/异常处理功能，不出现在普通设置首页。

### 2.5 一个功能尽量只有一个明确的“家”

例如：

- 字号 / 阅读主题 → `Aa`
- 目录 → `目录`
- 当前书摘录快速回顾 → 阅读页 `笔记`
- 完整整理笔记 → 一级导航 `笔记`
- 高亮 / 写感悟 → 选中文字后出现
- 书内搜索 → `⋯ 更多`
- 删除 / 更换封面 → 书库管理

避免同一个功能在多个地方重复出现。

---

## 3. Mobile 一级导航

手机端取消侧边栏和汉堡菜单。

底部固定三个一级入口：

**书库 / 笔记 / 设置**

“已读”不再作为一级入口。

---

# 4. 书库首页

## 4.1 顶部

只保留：

**书库　　　　　　　　　＋**

删除：

- 汉堡菜单；
- “个人阅读空间”；
- 常驻搜索框；
- 大号“导入图书”按钮。

`+` 负责导入 EPUB。

搜索功能暂时保留能力但不常驻首页；等未来书很多或全局搜索真正有价值时再重新设计入口。

---

## 4.2 继续阅读

目标：**第一眼看到、一次点击进入，但不要做成巨大 Hero 卡片。**

采用紧凑的单本横向卡片：

- 封面；
- 书名；
- 轻量阅读进度；
- 整张卡可点击；
- 不再额外放一个巨大“继续阅读”按钮。

继续阅读只显示：

**最近一次真正进入阅读页的那一本书。**

不是“阅读进度最高的书”。

如果当前没有未读完的最近阅读书籍，该模块直接消失，不显示无意义空状态。

---

## 4.3 我的书架

手机固定倾向三列书架。

每本书：

- 封面；
- 封面下必须显示书名；
- 不显示作者；
- 书名最多两行；
- 可使用封面底部极细进度线表达阅读进度；
- 0% 可不显示进度；
- 100% 以后可考虑轻量 `✓`，不需要醒目“已读”文字。

书名必须显示的原因：

**EPUB 封面可能缺失、失效、比例异常或本身很丑，封面不能成为唯一识别方式。**

---

## 4.4 书架排序

按“最近真正打开阅读”的时间倒序排列。

只有进入阅读页才更新最近打开时间。

以下操作不改变书架排序：

- 长按；
- 打开更多菜单；
- 更换封面；
- 编辑信息等管理操作。

Mobile 首页不常驻：

- “全部 / 阅读中 / 已读”筛选；
- 最近导入 / A-Z 等排序按钮。

未来如果需要展示“今年读了多少本”，应做独立的年度阅读档案/统计，而不是长期占据首页筛选栏。

---

# 5. 手机阅读页

## 5.1 默认状态：沉浸阅读

正常阅读时尽量让 UI 消失。

默认页面只保留：

- 正文；
- 很轻的阅读进度（例如右下角 `47%`）。

删除当前手机阅读页中的：

- 常驻顶部大工具栏；
- 正文外部明显大边框/卡片；
- 大量常驻图标；
- 左右翻页按钮视觉元素。

正文背景与阅读背景融成一个整体，避免“App 里面嵌了一个网页”的感觉。

---

## 5.2 基本手势

Mobile V1：

- **上下滑动**：全屏正文均可正常连续阅读；
- **轻点屏幕中央区域**：显示 / 隐藏阅读菜单；
- **长按 / 选择文字**：进入系统文字选择，并提供 BookReader 高亮/感悟功能；
- **点击脚注、链接**：优先执行正文内容本身的行为，不触发菜单。

一句话：

**滑动负责阅读，轻点中间负责 UI，长按负责文字操作。**

---

## 5.3 呼出阅读菜单

轻点中央后，正文位置必须保持不变，不因为工具栏出现而重排或跳动。

顶部：

**‹　　　　书名　　　　⋯**  
　　　　 当前章节

- `‹`：返回书库；
- 中间：书名 + 小号当前章节；
- `⋯`：低频功能。

底部：

**目录　　　Aa　　　笔记**

上下工具栏采用轻量、半透明/轻模糊风格，不做厚重大框。

再次轻点正文隐藏。

以后可以考虑数秒无操作自动隐藏，但不是 Mobile V1 的强制要求。

---

## 5.4 `⋯ 更多`

Mobile V1 只保留真正低频且有价值的功能：

- 书内搜索；
- 图书信息。

未来朗读功能稳定后，可以考虑加入：

- 朗读。

不要塞入：

- 字号 / 主题；
- 目录；
- 笔记；
- 高亮；
- 删除；
- 更换封面；
- 调试功能。

---

## 5.5 `Aa` 阅读设置

Mobile V1 核心只保留：

### 字号

不向用户强调 `17px` 之类的工程数字。

使用：

**A－　滑杆　A＋**

### 阅读主题

保留：

- 明亮；
- 纸张；
- 夜间。

未来可以增加：

- 行距；
- 左右边距。

当前手机设置中的以下内容全部移出普通用户界面：

- 分页诊断；
- 开始记录；
- 上一页测试；
- 下一页测试；
- PC 快捷键说明。

分页模式在真正稳定前不作为 Mobile V1 正式选项展示。

---

## 5.6 目录

现有目录逻辑保留，不做复杂重构。

手机端改为 Bottom Sheet，约 70%–80% 屏幕高度。

要求：

- 保留 EPUB 原有层级；
- 父章节与子章节有明显缩进；
- 父章节视觉略强；
- 当前章节明显高亮；
- 点章节后跳转正文并自动收起。

---

# 6. 文字选择、高亮与感悟

## 6.1 选择文字后的快速操作

iOS 已经提供：

- 拷贝；
- 查询；
- 翻译；
- 搜索网页等。

BookReader 不重复实现这些系统能力。

BookReader 自己只显示：

**高亮　　写感悟**

采用屏幕底部安全区上方的轻量操作条，而不是悬在正文中间的大胶囊。

删除单独的 `×` 关闭按钮。

用户取消系统选区或点击正文后，该操作条自然消失。

---

## 6.2 写感悟

点“写感悟”后使用 Bottom Sheet。

内容：

- 标题：写感悟；
- 当前选中的原文；
- 感悟输入区；
- 保存。

不离开阅读页。

目标：

**原文 + 此刻的想法。**

---

# 7. 阅读页里的“笔记”

阅读页底部的“笔记”不是完整笔记工作台。

它的职责是：

**阅读过程中快速回顾当前这一本书之前记过什么。**

采用约 75%–80% 屏幕高度的 Bottom Sheet。

内容：

- 本书标题；
- 摘录数量；
- 原文；
- 所属章节；
- 已有感悟；
- 如果没有感悟，显示 `+ 补充感悟`；
- 底部 `查看完整笔记 →`。

规则：

- 按原文在书里的顺序排列，而不是创建时间；
- 点某条摘录：Sheet 收起，跳到对应原文；
- 快速面板不承担复杂删除和管理；
- `+ 补充感悟` 调用同一套写感悟交互。

职责区分：

**阅读器里的笔记 = 快速回顾**  
**一级导航里的笔记 = 正式整理**

---

# 8. 完整“笔记”页面

当前页面整体结构可以保留，主要做减重。

## 8.1 顶部

删除：

- 汉堡菜单；
- “阅读与思考”；
- 大段功能解释。

顶部直接：

**笔记**

下方保留横向图书封面选择条。

---

## 8.2 当前图书

保留：

- 当前书名；
- 摘录数量；
- 打开图书入口。

“打开图书”改为轻量入口，不使用巨大按钮。

---

## 8.3 读后总结

功能保留。

但降低长期视觉权重：

- 空白时提供简洁输入；
- 已有内容时优先阅读展示；
- 点击“编辑”后再进入编辑状态；
- 不要让一个大型 textarea 永久占据大量屏幕。

---

## 8.4 原文与感悟

这是完整笔记页面的主体。

每条笔记平时以阅读状态展示：

- 原文；
- 所属章节；
- 回到原文；
- 我的感悟；
- 编辑/更多入口。

没有感悟时：

**+ 写感悟**

不要让每一条记录永久显示：

- 巨大 textarea；
- 巨大“保存感悟”按钮；
- 常驻红色“删除”按钮。

编辑时，只展开当前这一条。

删除等低频破坏性操作放入 `⋯`。

目标：

**从“很多编辑表单叠在一起”变成“我的阅读笔记”。**

---

# 9. 设置页面

当前 Mobile 设置页需要大幅简化。

核心原则：

**设置页应该告诉用户“一切是否正常”，而不是让用户理解系统内部怎么工作。**

一级内容只分四组。

---

## 9.1 同步

正常状态：

**OneDrive**  
● 已连接  
刚刚同步　　　　　　　　　管理 ›

同步中：

**OneDrive**  
◌ 正在同步 2 项

离线：

**OneDrive**  
○ 离线  
更改将在联网后同步

登录失效：

**OneDrive**  
! 需要重新连接　　　　　　重新连接

普通设置页不再常驻暴露：

- 重新登录；
- 连接并同步书库；
- 重新授权 OneDrive；
- 查看 OneDrive 目录；
- OneDrive 诊断；
- 手动同步大按钮；
- 各种 OAuth / 权限细节。

这些能力如仍需要，放到：

**同步 → 管理 → 高级**

诊断类内容可以只在开发版本显示。

---

## 9.2 数据与存储

保留：

- 离线图书；
- 回收站。

未来需要时再增加：

- 本地存储占用；
- 清理缓存等。

“申请保留本机数据”不应作为一个醒目的常规按钮。

如果 PWA / iOS 存在系统清理网站数据的客观风险，应以准确、易懂的方式说明，而不是让用户产生“我的数据是不是默认不保留”的恐慌。

---

## 9.3 外观

这里只控制 App 界面：

- 跟随系统；
- 浅色；
- 深色。

阅读正文自己的：

- 明亮；
- 纸张；
- 夜间；

仍然只在阅读页 `Aa` 中管理。

---

## 9.4 关于

保留：

- BookReader 版本；
- 检查更新：明确区分“已发现但尚未应用的新版本”“已检查且未发现新版本”与“检查/更新失败”；确认更新后才重新加载应用，本机书库和待同步数据保留。

---

# 10. 同步体验要求

同步应该从“用户操作”变为“系统行为”。

理想正常流程：

1. 打开 BookReader；
2. 本地书库立即可用；
3. 后台尝试恢复 OneDrive 会话；
4. 后台检查云端变化；
5. 自动合并/同步；
6. 完成。

用户不应该每天：

1. 打开设置；
2. 登录；
3. 跳微软网页；
4. 回 App；
5. 再点同步；
6. 等待；
7. 才能读书。

重新登录只能是偶发异常处理，而不能成为正常阅读流程。

普通页面不常驻“同步”按钮和长条同步栏。

同步成功可以轻提示：

**✓ 已同步**

随后消失。

真正异常才需要持续提示，例如：

**⚠ 1 项内容尚未同步**

而且异常也不能阻止本地阅读和记录。

---

# 11. Mobile V1 暂时不做 / 后续再做

以下功能有价值，但不进入当前第一轮核心施工：

- 稳定的左右分页与左右滑动翻页；
- 行距；
- 页边距；
- 朗读；
- 年度阅读档案；
- 阅读时长统计；
- 阅读时间线；
- 全局搜索（书名 + 正文 + 摘录 + 感悟）；
- 更复杂的已读/阅读中筛选；
- 高级 OneDrive 诊断 UI。

---

# 12. 后续施工方式

这份文档是“产品蓝图”，不是一次性施工任务。

禁止把整份 Mobile V1 直接扔给 Codex 一口气实现。

后续采用：

**确定一个任务 → 明确允许修改范围 → Codex 实现 → 手机实测 → 验收/修复 → Git 提交 → 再进入下一个任务。**

每个任务必须满足：

1. 目标足够小；
2. 明确哪些区域可以改；
3. 明确 Desktop UI 禁止被影响；
4. 默认禁止顺手重构共用底层；
5. 如果必须修改共用能力，先解释原因、影响和风险；
6. 修改前后验证 Desktop；
7. 修改前后验证 Mobile；
8. 数据格式/同步逻辑相关修改必须额外确认；
9. 一个任务验收稳定以后再进入下一个。

---

# 13. 建议施工顺序（仅作为路线图，具体任务后续逐个确认）

### 阶段 0：建立端侧隔离边界
先确保 Desktop UI 和 Mobile UI 有明确边界，不改变现有功能。

### 阶段 1：Mobile 导航骨架
取消手机侧边栏，建立 `书库 / 笔记 / 设置` 底部导航。

### 阶段 2：Mobile 书库首页
实现已经确定的首页结构、继续阅读、三列书架、最近打开排序。

### 阶段 3：Mobile 阅读页视觉与菜单
先做沉浸阅读、去边框、菜单显示/隐藏，不碰复杂分页。

### 阶段 4：Mobile 阅读辅助面板
实现 Aa、目录、更多。

### 阶段 5：文字选择与感悟
重做底部高亮/写感悟交互。

### 阶段 6：阅读中的本书笔记
实现快速回顾 Bottom Sheet。

### 阶段 7：完整笔记页面减重
在现有结构上优化，不推翻。

### 阶段 8：设置页面重构
把同步、存储、外观、关于重新组织成用户视角。

### 阶段 9：同步体验专项
单独审查 OneDrive 登录保持、本地优先、自动后台同步和异常恢复。

注意：

**阶段 9 属于高风险数据/同步改动，不能和普通 UI 改造混在同一个 Codex 任务中。**
